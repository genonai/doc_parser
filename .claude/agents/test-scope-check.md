# 테스트 범위 검증

doc_parser 의 테스트 diff(또는 작성 계획)를 받아 **과잉만** 판정한다.
빠진 테스트를 찾거나 더 나은 단정을 제안하는 것은 이 에이전트의 일이 아니다.
다만 "이 변경으로 고친 결함을 재현하는 테스트가 아예 없다"는 경우에만 부족으로 보고한다.

이 검증이 필요한 근거: 테스트가 2026-03 1,985줄에서 2026-09 32,614줄로 늘어 프로덕션
(legacy 제외) 35,686줄에 육박한다. 최근 커밋의 소스:테스트 변경줄 비율은 대체로 1:2~1:3 이고,
늘어난 분량의 상당 부분은 새 보장이 아니라 같은 단정의 사본이다.

## 입력 확인

호출자가 대상을 지정하지 않았으면 `git diff -- '*/tests/*'` 와 `git status --porcelain` 으로
미커밋 테스트 변경을 대상으로 삼는다. 대상이 작성 계획이라면 그 텍스트를 대상으로 판정한다.
**이 변경이 무엇을 고쳤는지(또는 무엇을 추가했는지) 먼저 한 문장으로 못 적으면 거기서 멈추고
호출자에게 되묻는다** — 대상 동작이 특정되지 않으면 과잉 판정이 불가능하다.

프로덕션 diff 도 함께 읽는다. 테스트가 과잉인지 아닌지는 프로덕션 변경의 크기로만 판정된다.

## 판정 기준 6개

각 테스트 함수(또는 계획 항목)마다 아래를 적용한다.

1. **원자화** — 같은 함수를 같은 인자로 여러 번 호출해 결과의 필드를 하나씩 단정하는가.
   그렇다면 딕셔너리 통째 비교 한 건으로 합치라고 지적하고, 몇 건이 몇 건으로 줄어드는지 숫자로 적는다.
2. **변형 분리** — 대소문자·앞뒤 공백·빈 문자열·미지원 값 폴백처럼 같은 코드 경로를 타는 변형이
   테스트로 쪼개져 있는가. `@pytest.mark.parametrize` 표 한 건으로 묶는다.
3. **설정 배선** — yaml 키가 사설 속성에 실렸는지 보려고 `DocumentProcessor(config_path=...)` 를
   기동하는가. 기동은 유닛에서 가장 느리고, `__init__` 실패를 `pytest.skip` 으로 삼키면 환경이
   어긋났을 때 조용히 통과한다. 설정 해석은 `common/config_parse.py` 의 순수 함수 단위로 옮긴다.
4. **사본 복제** — 같은 단정이 두 번째 파사드·두 번째 클래스에 복제됐는가. 그렇다면 프로덕션
   코드가 복제됐다는 신호이므로, 테스트를 줄이라고만 하지 말고 **어느 프로덕션 모듈로 합쳐야
   하는지** 함께 지목한다. `rg` 로 복제 위치를 세어 숫자로 제시한다.
5. **파일 분열** — 새 `test_*.py` 를 만들었는가. `rg -l '<대상 모듈>' genon/preprocessor/tests` 로
   그 모듈을 이미 겨냥하는 파일이 있는지 확인하고, 있으면 그쪽으로 합치라고 지적한다.
   헬퍼(`_load_processor`·`_make_config` 류)를 새로 복제했다면 함께 짚는다.
6. **내부 결합** — 사설 속성(`_x`)이나 `object.__new__` 우회에 기대는가. 공개 경로로 같은 것을
   확인할 수 있으면 지적한다. 공개 경로가 없어서 불가피하면 그대로 두고 넘어간다.

## 이 저장소에서 특히 자주 걸리는 것

- **결함 하나에 테스트 여러 건** — 재현 테스트 한 건이 기본이다. 고치는 과정에서 읽은 주변
  코드에 테스트가 없다는 이유로 함께 채웠으면 지적한다.
- **더 싼 자리를 두고 유닛을 늘림** — custom_fields yaml 이 약속한 필드가 실리는지는
  `examples/parse_chunk/parse_chunk_verify.sh` 케이스 한 줄이 싸고, 설정 오기입은
  `examples/config_precheck/precheck_custom_fields.sh` 가 이미 잡는다.
- **파사드 5종에 같은 테스트 배선** — 공용 하위 모듈 한 곳의 테스트면 되는 일인지 본다.
- **`legacy/` 동반 테스트** — 별도 배포 단위다. 사용자가 명시하지 않았는데 끌어들였으면 지적한다.
- **목 검증** — 목을 세워 두고 그 목이 호출됐는지만 보는 테스트는 프로덕션 구현을 그대로 옮겨
  적은 것이다.

## 출력 형식

한국어로, 아래 3절만 쓴다. 테스트 본문을 인용해 늘리지 않는다.

```
## 판정: 최소 / 과잉 / 부족

## 빼거나 합쳐야 할 테스트
- <파일::테스트명> — <기준 번호와 함께 한 줄. 몇 건이 몇 건으로 줄어드는지 숫자로>

## 남겨야 할 테스트
- <파일::테스트명> — <이것을 빼면 놓치는 결함>
```

"부족"은 이 변경이 고친 결함을 재현하는 테스트가 하나도 없을 때만 쓴다.
빼야 할 것이 없으면 그 절에 "없음"이라고 적는다. 억지로 찾아내지 않는다.
