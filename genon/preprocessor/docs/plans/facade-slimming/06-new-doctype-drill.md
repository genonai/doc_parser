## 이 단계가 필요한 이유

01~05 는 "프로세서가 작아졌다" 를 증명한다. 그것이 곧 **"고객이 새 문서를 스스로 처리할 수
있다"** 를 증명하지는 않는다. 이 단계는 실제 문서로 그것을 직접 확인한다.

리팩터링의 성공 여부를 판정하는 것은 줄 수가 아니라 이 드릴의 결과다.

## 두 갈래

### A. 기존 보유 문서 중 복잡한 것

이미 처리되는 문서다. 목적은 **리팩터링 뒤에도 복잡한 원천이 그대로 처리되는지** 확인하는 것.
골든 대조가 이미 커버하지만, 드릴에서는 사람이 산출을 직접 읽어 본다.

실측한 복잡도 상위:

| 문서 | 복잡한 이유 |
|---|---|
| `monimo_product_hpp_wcms_sample.json` | depth 5 / 고유 키 28개, `json_semantic` 풀 캡처 |
| `monimo_event_real_sample.json` | depth 4 / 고유 키 **35개**, 실 payload 스키마 |
| `monimo_product_hpp_rich_table_sample.json` | depth 5 / 키 25개 + rich cell 표 |
| `monimo_cs_hpp_rich_table_sample.html` | rich cell 표 + colspan 안내 셀 |
| `monimo_cs_hpp_large_table_sample.html` | 대형 표 분할 경로 |
| `monimo_cs_hpp_marker_real_dom_sample.html` | h태그 없이 도형 마커로만 계층 표현 |
| `.INC_235488_02_20260626103138.html.parsed` | 비표준 확장자 + md/HTML 혼합 |
| `monimo_stock_insight_sample.xlsx` | 보유 xlsx 중 최대 |

비-모니모 중에서도 표가 어려운 것을 섞는다 — `html_tables.html`, `tablecell.docx`,
`hwp_sample_table.hwp`.

### B. 신규 생성 문서 — 변경 가능성이 큰 구조

**보유 문서와 다른 구조를 일부러 만든다.** 현재 보유 JSON 은 depth 5 / 키 35개가 최대이고
구조도 비교적 얌전하다. 실제 신규 원천에서 흔히 나오는 변형을 재현한다.

05 의 경계 조사에서 나온 "이름으로 구분이 안 되는" 4가지를 축으로 삼는다.

| # | 픽스처 | 노리는 변형 | 예상 |
|---|---|---|---|
| B1 | 동명 키 충돌 | `title` 이 루트와 중첩 양쪽. 필요한 것은 **깊은 쪽** | 설정 불가 → 코드 |
| B2 | 동적 키 | 상품코드가 key (`{"P001": {...}, "P002": {...}}`) | 설정 불가 → 코드 |
| B3 | 2단 중첩 레코드 | `groups[].items[]` — 레코드가 두 겹 배열 안 | `records` 이름 검색으로 될 수도 |
| B4 | 조건부 선택 | 형제 노드 `type` 값에 따라 본문 필드가 갈림 | 설정 불가 → 코드 |
| B5 | 타입 흔들림 | 같은 필드가 문자열/숫자/배열/null 로 섞임 | 값 파이프라인으로 흡수되는지 |
| B6 | 표가 HTML 문자열 | `"detail": "<table>…</table>"` 로 박힘 | `transform: html_text` 로 될 것 |
| B7 | 문서형+레코드형 혼합 | 헤더 메타 + 레코드 배열이 한 파일에 | 어느 extractor 로 갈지 |
| B8 | 깊은 중첩 | depth 8 (보유 최대 5) | 이름 검색이 버티는지 |
| B11 | 인코딩 | UTF-8 BOM / CP949 | **코드 필요(1줄)** |
| B12 | JSONL/NDJSON | 줄 단위 레코드 피드 | **코드 필요** |
| B13 | null·결측 키 | 선언한 필드가 없거나 null | `default`/`require`/`on_missing` 상호작용 |
| B14 | 이스케이프된 중첩 JSON | `"detail": "{\"a\":1}"` | B6 의 형제 |
| B15 | 빈 배열 / 0건 | `records` 는 있는데 요소 0 | 에러 경로가 갈림 |
| B16 | **doc_type 충돌** | 새 설정이 기존 doc_type 과 겹침 | 즉시 예외. **남의 doc_type 을 죽이는 경로** |
| B17 | 대량 레코드 + LLM 필드 | 레코드 5,000건 | 비용·지연 축 |

**B9(멀티헤더 xlsx)·B10(중첩 표 html)은 트랙 A 로 옮긴다.** 축이 다르다 — JSON 도 아니고
"이름으로 구분 안 됨" 도 아니다. 그 둘의 고칠 자리는 `facade/chunking/table_html.py` 등
공용 표 직렬화라 **거의 확실히 "공용 모듈 필요" 판정이 나오고 04 의 실패로 집계된다.**
드릴 결론을 흐린다.

추가된 B11~B17 의 근거:

- **B11** — `parser_processor.py:1513` 이 `encoding="utf-8"` 하드코딩. BOM JSON 은 `json.load` 가
  하드 실패한다. 국내 기업 원천에서 가장 흔한 사고이고 fix 는 facade 1줄이다
- **B12** — `_load_json_payload` 정규화 훅의 교과서적 사례
- **B15** — `collect_records` 가 None 반환 vs 빈 리스트에 따라 에러 경로가 갈린다
- **B16** — `parser_processor.py:1205-1212` `_single_json_match` 가 즉시 예외를 던진다.
  **고객이 설정 하나 추가해 기존 doc_type 을 죽일 수 있는 유일한 경로**이고,
  합격 기준 4(골든 차이 0)가 정확히 이것을 잡아야 한다
- **B17** — `_apply_llm_fields`(`:1546`)가 record 스코프에서 건당 LLM 호출. 비용·지연 축이 없었다

**B1·B4 는 코드가 필요할 것으로 예상되며, 그것이 이 드릴의 핵심 대상이다.**
B2(동적 키)는 05 재조사에서 **json_semantic 이면 설정 0줄로 본문이 들어온다**는 것이 확인됐다 —
"레코드 1건 + 그 키에 딸린 메타데이터" 형태일 때만 코드가 필요하다.
설정으로 되는 것(B5·B6 등)은 "코드 없이 됐다" 는 결과 자체가 성과다.

**코드가 필요할 때의 자리는 `_load_json_payload` 다**(05 참조). 드릴 3단계에서 고객이
공용 모듈로 가면 그것은 04 가 이 훅을 안내하지 못했다는 뜻이다.

생성 스크립트는 `examples/parse_chunk/` 의 기존 관례를 따른다
(`make_product_hpp_fields_sample.py` 등이 이미 그 방식이다). 손으로 만든 파일이 아니라
**스크립트로 재생성 가능**해야 축을 나중에 바꿀 수 있다.

## 드릴 절차

각 픽스처마다 이 순서로 한다. **순서를 지키는 것이 중요하다** — 코드부터 손대면
설정으로 되는 것도 코드로 풀게 된다.

1. **그대로 넣어 본다.** 어디서 무엇이 누락되는지 기록한다.
2. **설정만으로 시도한다.** `custom_field_*.yaml` + 등록 블록.
   여기서 되면 코드 변경 0 이고, 그 사실을 기록한다.
3. 안 되면 **facade 코드를 고친다.** 이때 아래를 기록한다.
   - 고친 파일 수
   - 고친 위치가 04 에서 정한 "고칠 자리" 안이었는가
   - 변경 줄 수
   - 원인을 찾는 데 걸린 시간(파일을 얼마나 읽어야 했는가)
4. **청커 산출까지 확인한다.** 파서 출력만 보면 안 된다 — element 의 `category` 가
   `{"tabular_row", "custom_fields_row", "faq_row"}` 중 하나가 아니면 metadata 가 청크에
   안 실리거나 element 가 통째로 버려진다(05 의 "파서 → 청커 element 계약" 참조).
5. **골든 대조를 돌린다.** 그 수정이 **기존 doc_type 산출을 바꾸지 않아야** 한다.
6. 결과를 기록하고 **수정을 되돌린다.**

## 합격 기준

이 드릴은 리팩터링의 최종 판정이다. 아래를 모두 만족해야 통과다.

| 기준 | 값 |
|---|---|
| 고쳐야 하는 파일 | facade **1개** (공용 모듈을 건드려야 하면 실패) |
| 고치는 위치 | 04 에서 정한 "고칠 자리" 안 |
| 변경 줄 수 | 30줄 이하 |
| 기존 doc_type 산출 | 골든 대조 차이 **0** |
| 청커 산출 | 새 doc_type 의 metadata 가 청크에 실림 |
| 원인 파악 | 파일 전체를 읽지 않고 도달 가능 |

**"facade 1개" 의 정의를 먼저 못박는다.** 배포 형태가 둘이라 셈이 달라진다.

- 코드서빙형: 루트 `main.py` 가 facade 5개를 한 서버에 마운트
- 외부 사이트형: facade **한 개**만 `preprocessor.py` 로 마운트. `IS_PARSER` 는 parser 에만,
  `IS_CHUNKER` 는 chunking 에만 있어 **한 서빙이 파싱과 청킹을 둘 다 할 수 없다**

고객은 서빙 2개를 운용하므로 실제 작업 단위는 "배포본 2개" 다. 그리고 고객이 여는 파일
이름은 `parser_processor.py` 가 아니라 `preprocessor.py` 다. 자세한 것은
[07](07-customer-change-lifecycle.md) C 항목.

**측정 방법을 정한다.**

- **"30줄"** — `git diff --numstat -- genon/preprocessor/facade` 로 **경로를 스코프**해서 센다
  (안 그러면 `sample_files/drill/` 픽스처가 섞인다). `added + deleted` 인지
  `max(added, deleted)` 인지 먼저 정한다 — 15줄 교체가 30이 되어 임계에 딱 걸린다.
  드릴 수정은 커밋하지 않으므로 워킹트리 diff 를 쓴다.
  단 `.artifacts/` 와 파생 `.pdf` 가 생기므로 **`git status` 로 판정하는 절차는 넣지 않는다**
- **"파일 전체를 읽지 않고 도달"** — 자기보고 대신 **04 가 정하는 "고칠 자리" 를
  `(파일, 심볼, 줄범위)` 앵커 목록으로 먼저 고정**하고, "고친 위치 ∈ 앵커 목록" 이라는
  **이진 판정**으로 바꾼다. `git diff` 의 hunk 위치로 자동 검증되고,
  부수 효과로 04 의 산출물이 검사 가능한 형태가 된다.
  보조 증거로 `.claude/hooks/large-file-read-guard.sh`(1,200줄 초과 파일의 무인자 Read 차단)에
  몇 번 걸렸는지를 센다

**두 기준은 일부 픽스처에 적용되지 않는다.**

- **B16(doc_type 충돌)** — `_single_json_match`(`parser_processor.py:1205`)가 **설정 로드 시점에
  예외**를 던지므로 골든은 "차이 0" 이 아니라 **전 케이스 기동 실패**로 끝난다.
  그것이 곧 합격 신호임을 따로 적는다
- **"청커 산출에 metadata 가 실림"** — 신규 doc_type 은 골든이 없다.
  `parse_chunk_verify.py` 의 단정 방식(required/constants)을 재사용한다

**"공용 모듈을 건드려야 한다" 는 결과가 나오면 그것은 드릴 실패가 아니라 04 의 실패다** —
고칠 자리를 잘못 정한 것이므로 04 로 돌아간다.

## 범위 주의

**드릴에서 만든 facade 수정은 커밋하지 않는다.** 이 작업은 "가능한가" 를 검증하는 것이지
신규 doc_type 을 추가하는 것이 아니다. 신규 기능 추가 금지 원칙이 여기에도 적용된다.

남기는 것은 **픽스처와 절차와 결과 기록**이고, 그것이 다음 고객 요청 때 그대로 쓰인다.

픽스처는 `parse_chunk_verify.py` 의 `CASES` 에 넣지 않는다 — 대응 설정이 없으므로
전부 SKIP 되거나 실패한다. 드릴 전용 목록으로 분리한다.
