# facade 정리 — 작업 계획 (#363)

parser / chunking 프로세서를 **고객이 직접 읽고 수정할 수 있는 크기**로 줄인다.

## 이 작업의 목적

현재 프로세서가 제공하는 기능을 고객 사이트에 제공하되, **기존 방식으로 처리하기 어려운
새 문서를 만났을 때 고객이 간소화된 parser / chunking 프로세서를 직접 고쳐서 해결**할 수
있게 만드는 것이 목적이다.

따라서 이번 작업의 산출은 세 가지다.

1. 프로세서가 읽을 수 있는 크기가 된다 (01~03)
2. 고칠 자리가 어디인지, 지금 있는 기능으로 어디까지 되는지가 드러난다 (04~05)
3. 실제 문서로 "정말 되는지" 를 확인한다 (06)

## 최우선 원칙 두 가지

### 1. 동작 동일성

**리팩터링 뒤 parser / chunker 의 산출이 기존과 같아야 한다. 다른 모든 목표에 우선한다.**

크기를 줄이는 것도, 표면을 정리하는 것도 이 조건을 깨면서 하지 않는다.
그래서 00번(골든 기준선)이 다른 모든 작업보다 먼저다.

### 2. 신규 기능을 추가하지 않는다

이번 작업은 **정리와 재배치만** 한다. 새 설정 키, 새 확장 메커니즘, 새 플러그인 지점을
만들지 않는다. 고객의 새 요건은 **지금 있는 기능**으로 푸는 것이 전제이고,
그것으로 안 될 때 고객이 프로세서 코드를 고치는 것이 이번 리팩터링이 여는 길이다.

기능 추가 아이디어가 나오면 별도 이슈로 분리한다.

## 남은 것

- **07-A 는 [08](08-customer-facade.md) 이 A3(고객 소유 `preprocessor.py` 를 배포 범위에서
  분리)로 확정했다.** facade 가 100줄이 되어 벤더 로직과 고객 수정의 분리가 성립하기 때문이다.
  B(번들 경고)·C(배포 단위 2개)·D(고객 골든)는 08-5 에서 문서로 처리한다.
- 별도 이슈 후보 5건: 빈 레코드 배열에서 청커 예외(06 B15), 청커의
  `page_batch_size` 전역 오염(01), xlsx 기본값·`thinking` 인자 드리프트(02),
  sections/document 표 평문화 렌더러 주입(05 경계 ⑤), 배열 metadata 의 repr 표기(06 B5).

착수 중 내린 결정 4가지(계획에 없던 것):

1. **골든에서 빼는 케이스 3종** — `card01.flat.html`(개인 디렉터리), `hwp_sample_table.hwp`
   (외부 실행파일 `convtext` 필요), `pptx_sample.pptx`(PPT→PDF 변환본이 실행마다 달라져
   layout VLM 캐시가 매번 miss, 실측 17건). 뺐다는 사실은 실행할 때마다 출력한다.
   docling PDF 경로는 `pdf_sample.pdf` 가 덮으며 이쪽은 안정적이다.
2. **노이즈 측정은 record/check 와 같은 캐시 스코프로** — 회차마다 스코프를 나누면 2회차가
   LLM 을 다시 불러 그 답의 흔들림까지 노이즈로 잡힌다(실측: text/n_char/SUMMARY_TEXT 등
   58개 산출물이 어긋났다). 스코프를 맞추면 남는 노이즈는 `reg_date` 하나다.
3. **3a 에서 `GenericDocumentLoader` 는 facade 에 남긴다** — `get_loader` 가 곧
   "어떤 확장자를 어느 로더로 보내는가" 라서 04·05 가 고객에게 읽히려는 바로 그 표다.
   옮긴 것은 `HwpDocumentLoader`/`DocxDocumentLoader`(순수 docling 컨버터 조립)뿐이고,
   그 덕에 계획이 걸림돌로 꼽은 두 가지(공용 모듈의 docling import, 공용 모듈이 어느
   `GenosServiceException` 을 쓰나)가 함께 사라졌다.
4. **A/B 대조는 `*_wip.py` 대신 "HEAD 사본 vs 현재 트리" in-process 비교로 했다** —
   `git show HEAD:<파일>` 을 별도 모듈로 로드해 같은 프로세스에서 양쪽 인스턴스를 만들고
   `__dict__` 를 통째로 대조했다. WORKFLOW 의 임시본 방식보다 이쪽이 `__init__` 리팩터링에
   더 맞는다 — 임시본은 "wip == 현재 트리" 만 증명하는데, 이 방식은 "현재 == 착수 전" 을
   직접 증명한다. 임시본을 만들지 않았으므로 종료조건 4·5(임시 파일 삭제·`git status` 청결)는
   자동으로 만족한다.
5. **드리프트 2개는 고치지 않고 플래그로 보존** — `formats.xlsx.processing_mode` 기본값
   (parser=tabular / 나머지=docling)과 `MetadataEnricher` 의 `thinking` 인자
   (intelligent 만 안 넘긴다). 통일은 동작 변경이라 별도 이슈다.

— 04 의 표면 정리가 그만큼 중요하다.

parser 목표치는 검증에서 **~1,000 이 350~450줄 낙관**으로 판정돼 상향했다. 산술:
2,497 − 387(02) − 765(3a+3b+3c) = 1,345 이고, 테스트가 요구하는 얇은 래퍼를 더하면
1,400~1,450 이 현실적이다. **이 저장소 자신의 대용량 파일 가드 임계가 1,200줄이므로
리팩터링 후에도 그 선을 넘는다** — 04 의 표면 정리가 그만큼 중요해진다.

## 검증 원칙

- A/B 대조와 골든 대조가 1차 관문이다. 유닛 테스트는 그 다음이다.
- 유닛은 **바꾼 모듈을 쓰는 파일만** 지정해서 돌린다. 전체는 201초 + 사전 실패 21건이라
  단계마다 돌리면 비용이 크다.
- 전체 유닛은 각 단계 **종료 시 1회**와 PR 직전에 돌린다.
- 항상 `--color=no` 를 유지한다. `addopts` 의 `-p no:cacheprovider` 때문에 `--lf` 는 쓸 수 없다.


## 검증 이력

계획은 서브에이전트 독립 검증을 거쳤다. 검증에서 나온 정정은 각 문서에 반영돼 있다.

| 대상 | 상태 | 주요 결과 |
|---|---|---|
| 03 (parser 분해) | 완료 | 9건 정정. 3c 는 순수 함수가 아니고 위험이 가장 높다 |
| 05 (기능 경계) | 완료 | v2 가 이미 출고 표기. `transform` 은 2종이 아니라 9종. 경계는 4가 아니라 8 |
| 고객 개발자 관점 | 완료 | 07 신설의 근거. 고객이 읽는 매뉴얼과 골든 커버리지 구멍 |
| 01·02 기술 타당성 | 완료 | 01 의 미호출 판정 15건은 전부 참. 다만 삭제 범위가 필수 대입 2개를 삼켰고, 02 는 속성 집합이 갈라져 있어 단순 이동이 아니다 |
| 검증 설계 타당성 | 완료 | **골든이 3c 의 절반을 실행하지 않는다.** LLM soft-fail 이 "빈 값으로 일치" 를 만든다 |

**5건 전부 완료됐고 모든 문서에 정정이 반영됐다.**

착수 순서에 영향을 주는 결론 세 가지:

1. **07 이 가장 먼저다** — 고객 수정분이 릴리스에서 어떻게 되는지가 정해지지 않으면
   04~06 의 목적이 성립하지 않는다.
2. **00 이 그다음이고, `--output-format` 추가가 그 안에 포함돼야 한다** —
   그것 없이는 03 의 3c 가 안전망 없이 진행된다.
3. **01 은 착수 가능하다** — 미호출 판정이 독립 검증을 통과했다. 삭제 범위만 개정판대로 쓴다.
