# 묶음 3 — 동시 요청 테스트와 속도 측정

묶음 2 에서 띄운 리비전에 클라이언트로 parse·chunk 요청을 순차 한 번, 동시로 한 번 보내고, 응답과 서빙 로그로
요청 간 간섭과 처리 시간을 본다. 대조군과 수정본 리비전에 같은 클라이언트·같은 문서·같은 인자로 한 번씩 돌린다.

## 무엇을 보나

| 지표 | 보는 법 | 간섭이면 |
|---|---|---|
| R1 enrichment 토글 | 같은 문서를 `img_desc`·`table_desc`·`doc_summary` 를 켠 요청(on)과 끈 요청(off)으로 섞어 보낸다 | off 응답에 그림 설명·문서 요약이 들어오거나, on 응답이 순차 실행보다 설명·요약을 잃는다 |
| R2 쪽별 청크 수 | 청크의 `n_chunk_of_page` 가 그 쪽의 실제 청크 수와 같은지 | 다른 문서의 값으로 덮여 어긋난다 |
| doc_type 설정 | doc_type 별 custom_fields 문서(모니모 매니페스트)의 청크 필드 집합이 순차 실행과 같은지 | 다른 doc_type 의 설정이 섞여 필드가 생기거나 빠진다 |
| 실패 | 응답 `code` | 0 이 아니다 |
| 속도 | 순차 합계 대비 동시 벽시계, 요청별 소요 시간 | — |

VLM(dots.mocr)을 거치는 문서는 실행마다 레이아웃 응답이 조금씩 달라 청크 수가 순차와 다를 수 있다. 이것은 간섭이 아니다.
판정은 VLM 을 거치지 않는 문서(hwp·hwpx·docx·모니모 텍스트형)의 일치와, R1·R2 지표로 한다.

## 준비물

- 클라이언트: `genon/preprocessor/tools/code_serving/concurrency_test.py`(표준 라이브러리만), 매니페스트
  `monimo_manifest.json`(같은 폴더, `parse_chunk_verify` 의 케이스 표에서 뽑은 doc_type 32건).
- 문서: 서빙 파드에서 보이는 NFS 폴더(`<DOC_DIR>`)에 샘플 문서 7종의 `__on`·`__off` 사본 14개와 매니페스트 파일 32개.
  일반 샘플은 `genon/preprocessor/sample_files/`, 모니모 샘플은 `sample_files/monimo/`·`sample_files/json/` 에 있다.
- 실행 위치: 같은 클러스터의 코드스페이스. 리비전 서비스(`code-serving-<ID>-<REV>:8080`)를 직접 부른다.

## 절차

### 1. 서빙 로그를 받기 시작한다 (배스천)

```bash
kubectl -n <NAMESPACE> logs -f <POD> -c <CONTAINER> --since=1s > /tmp/rev<REV>_logs.txt &
```

### 2. 클라이언트를 돌린다 (코드스페이스)

동시 수는 워커 수보다 크게 잡아 한 프로세스에 요청이 여러 개 겹치게 한다(워커 5개면 15).

```bash
python3 concurrency_test.py --base http://code-serving-<ID>-<REV>:8080 --docdir <DOC_DIR> --out ./rev<REV> --phases solo,concurrent --workers 15 --manifest monimo_manifest.json --param log_level=4
```

`./rev<REV>/run.log` 에 단계별 표와 "간섭 징후" 목록이, `results.json` 에 요약이, `raw/` 에 원 응답이 남는다.

### 3. 로그를 멈추고 결과를 모은다

```bash
kill %1
```

### 4. 리비전을 바꿔 같은 절차를 반복한다

대조군이 끝나면 대조군 리비전을 내리고 수정본 리비전을 띄워(묶음 2) 1~3 을 그대로 반복한다.

## 결과 해석

- **간섭**: 대조군에서 R1·R2·doc_type 징후가 나오고 수정본에서 사라지면 #481 이 효과가 있는 것이다. 대조군에서도 0건이면
  간섭이 재현되지 않은 것이고, 이 테스트로는 #481 을 판정할 수 없다(동시 수를 늘려 다시 본다).
- **속도**: 같은 리비전 안에서 순차 합계 대비 동시 벽시계가 처리량 이득이다. 대조군과 수정본의 동시 벽시계 차이가 코드 변경의
  속도 효과다. `ocr_mode` 를 같은 값(`disable`)으로 둔 비교라 #482 의 두 번째 변환 제거 효과는 여기 나타나지 않는다.

## 이 검증의 결과

조건: 같은 코드서빙, 베이스 이미지 2.2.5, 워커 5, CPU 1·메모리 16Gi, 같은 리소스 폴더(`ocr_mode: disable`), 46건.

| 리비전 | 코드 | 순차 | 동시 15 | 간섭 징후 | 실패 |
|---|---|---|---|---|---|
| 대조군 | develop 49d8f176(#482·#481 전) | 741초 | 244초 | 0 | stock_insight 2(설정 불일치) |
| 수정본 | #481+#482(28f8b94f) | 709초 | 661초 | 0 | 같은 2 + chunk 503 1회 |
| 수정본 + `OMP_NUM_THREADS=1` | 같음 | 355초 | 191초 | 0 | 같은 2 |

- 두 리비전 모두 요청 간 간섭이 없었고, 수정본은 대조군과 같은 결과를 냈다(회귀 없음).
- 수정본 동시 661초는 PPTX 두 건이 같은 시각에 docling 변환에 들어가 각각 약 560초 걸린 탓이다. 같은 두 건을 수정본에 다시 보내면
  동시에는 변환 500초 안팎, 차례로는 요청 전체 96·78초였다. PPT 변환 코드는 두 버전이 같다.
- 원인은 CPU 과다 구독이다. 파드 CPU 한도 1 코어인데 프로세스가 CPU 4개를 보고 스레드 수 환경변수가 없어 torch 가 여러 스레드를 띄운다.
  측정 중 CPU 제한에 걸린 주기가 47% 였다. **리비전 환경변수에 `OMP_NUM_THREADS=1`(파드 CPU / 워커 수)을 넣고 다시 재는 것을 권한다.**
- enrichment 를 켠 요청은 외부 LLM 이 한 번씩 응답 없이 멈췄다가 읽기 시간 초과(360초) 뒤 재시도로 회복했다. 속도 비교는 동시 벽시계와
  LLM 을 거치지 않는 off 요청으로 한다.
- `OMP_NUM_THREADS=1` 로 다시 띄운 리비전에서 PPTX 두 건을 동시에 보내면 변환이 61·63초(차례로는 약 30초)였다. 겹쳐도 1 코어를 둘이 나눠 쓰는
  2배로 줄었고, CPU 제한에 걸린 주기도 47% 에서 23% 로 내려갔다. 리비전에는 이 환경변수를 기본으로 넣는다.
- 순차 355초는 이 실행에 외부 LLM 정체가 없었던 몫이 크다(enrichment 를 켠 표 PDF 92초, PPTX 94초). LLM 을 거치지 않는 off 요청은
  세 리비전이 같은 범위이고, PPTX off 만 77·70→57초로 줄었다(CPU 변환 구간).
- 대조군은 `OMP_NUM_THREADS` 없이 쟀으므로, 코드만 다른 비교를 하려면 대조군도 같은 환경변수로 한 번 더 잰다.
- 분석 보고서 4-8 에 같은 내용을 수치와 함께 정리했다.
